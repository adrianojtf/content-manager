# Technical Specification — Community Management

**Status:** Draft. Local OAuth-backed account connection is implemented for YouTube, Instagram professional accounts, Facebook Pages, and TikTok Business, with deterministic tests. Provider live access/App Review remains pending. TikTok uses a runtime-configured app-generated authorization URL and validates `video.list`, `comment.list`, and `comment.list.manage`; the documented refresh request matches the adapter, with approved-app verification still pending. TikTok documents a distinct short-term account-token revoke endpoint, but the application does not expose or call it. Manual network/content sync, manually initiated workflow phases, 30-day retention, per-comment manual sends, and the semi-automatic send-all action for individually approved replies are decided. AI response generation requires comment analysis; creator-authored text does not. The Phase 1 creator communication policy is fixed rather than configurable: no workflow automatically generates or sends a response, Jev risk/evaluation results are advisory, and an explicit per-comment send or final confirmation for approved rows can dispatch a saved response after per-comment capability/authorization checks. No numeric risk threshold or account-level policy setting is introduced. Response generation is configurable between Google Gemini Flash-Lite and OpenAI GPT-6 Luna, with Gemini as the pilot default. Local creator-reply synchronization is implemented where author evidence is available; TypeSafe API account/credit verification, live request validation, and Gemini Free-tier data-use acceptance remain open.

Here, “no workflow automatically generates” excludes background or implicit behavior. The creator may explicitly request the documented per-video composite evaluation/generation action; sending is a separate explicit action and can only include individually approved, saved responses.

## 1. Scope

For Phase 1, organize comments under a social-network tab, then publication/video, then comment. Fetch comments only after an explicit manual sync action for one publication/video or the currently visible publication page on one selected network; the browser does not start a whole-network sync and no operation runs in the background. Normalize and tenant-scope comments, preserve provider identifiers, and retain them for 30 days after the last successful sync. Every standalone workflow phase is initiated explicitly; the per-video semi-automatic dialog is itself an explicit composite request for analysis-if-needed followed by generation. No other phase is automatically triggered. Comment analysis and AI response generation may run per comment, publication/video, or selected network, with independent per-comment results. AI response generation requires comment analysis; creator-authored response text does not. Response evaluation is optional, manually requested, and advisory. Every external reply requires explicit creator action and per-comment capability/authorization checks; the semi-automatic send-all action is separate from generation and limited to individually approved saved responses.

### CreatorDesk browser application

- Serve the comments application at `/` from the API origin and use the same-origin REST API; do not hardcode provider credentials or include simulated social/JEV results.
- The profile/settings view lists connected accounts through `GET /social/accounts` without provider reads. OAuth connection uses the configured provider routes; Facebook Page candidates require explicit selection through the existing selection API. Do not collect OAuth secrets in the browser.
- Preserve the prototype hierarchy: network tabs, connected-account selection, publications, then expandable comments. Search and reply-state filters apply to the current publication pages; publication/comment loading, unavailable states, and errors reflect API responses rather than fabricated counts.
- Each network tab badge shows the persisted unanswered-comment count for that platform — comments with `appReplied = false` and `externalReplyStatus = 'NOT_REPLIED'` — not the number of loaded publications. The badges come from `GET /social/comments/summary`, are loaded on every screen load and refreshed after comment syncs, reply sends, and workflow batches, and are kept only in memory. Until a summary loads, the badge shows `—`.
- The summary endpoint also feeds the four statistics cards with tenant-wide totals across all platforms: stored comments, unanswered comments (same rule as the badge), unevaluated comments (no non-failed `COMMENT_ANALYSIS_CREATED` event), and successful `MANUAL_REPLY_RESULT` sends recorded on the current UTC day. Counts exclude expired comment/event rows.
- Fetch only the active network, then paginate each connected account's publications with a default page size of five and supported choices of 10 or 25. Send `platform` and `pageSize` with `GET /social/publications`; provider cursors stay opaque. Keep only each active account's current page in browser state, replace it on navigation/network change, and discard comment/workflow cache for videos no longer on a current page.
- The main sync action snapshots the currently visible videos after account selection and search/status filters, then calls the per-publication comment-sync route once per video, sequentially. Do not call `POST /social/workflow-batches` with platform scope from this control. Report current video, completed/total counts, and per-video success/failure through visible text and an `aria-live` status; a failure must not stop remaining videos. Comment-page continuation remains an explicit per-video action.
- The same page-level sync also runs automatically — with the same progress reporting and per-video failure tolerance — after publications load on the initial comments screen, on every network tab switch, when returning to the comments screen, and after a successful publication page navigation. It only runs when the publication load succeeded, and it refreshes the comment summary once after the batch completes rather than per video. While a page-level sync runs, the publication list is not rebuilt per video: it stays frozen under a visible sticky loading indicator and re-renders once when the batch completes.
- Each publication card also offers a semi-automatic reply dialog scoped to that one video and connected account. Opening it explicitly calls `POST /social/workflow-batches` with `operation: sync` and `scope: publication`, which synchronizes every comment page for that publication only, then loads the persisted comments. The queue includes only comments with a successful per-comment sync outcome, `appReplied === false`, and `externalReplyStatus === NOT_REPLIED`; exclude stale rows from failed pages, confirmed replies, and `UNKNOWN` rather than assuming they are unanswered.
- The creator explicitly starts the dialog's combined evaluation-and-generation action. It processes eligible comments sequentially, evaluates only comments without a successful analysis, and generates separate `pt-BR`, `en-US`, and `es-ES` suggestions for each comment. Keep independent outcomes and show partial failures without discarding successful comments or variants. This explicit composite action is the only workflow entry point allowed to run analysis followed by generation without another click; it never sends a reply.
- Show each queued comment beside its selected response variant. The creator can choose a response language and a one-time primary-tone override per comment; the override inherits the effective profile's modifiers/note, is validated by the API, is snapshotted on every generated variant, and never changes the saved account or global tone profile. Choosing a different tone in a row is the explicit per-comment regeneration action: it regenerates that row’s variants using the existing comment analysis without re-evaluating the comment, and a failed regeneration leaves the row eligible for an explicit retry.
- Row, selected-row, and all-row approval are review-only actions. Save any edited AI response first through the existing append-only revision route so the original suggestion and human revision remain auditable. Approval never calls a send route; its marker lasts only for the current in-memory dialog run. A separate “send all approved” action requires a final confirmation and includes only approved, saved, reply-capable rows with no prior attempt for that exact version. It calls the existing per-comment send route serially, keeps every attempt/result in that comment's audit history, reports per-row outcomes, continues after individual failures, stops on `SOCIAL_PROVIDER_RATE_LIMITED`, and never retries failed or ambiguous attempts. No batch-send endpoint or randomized delay is introduced.
- Preserve the stable `SocialProviderError` code returned by the comment-sync HTTP route. Show a generic failure badge plus an adjacent localized reason card selected by `(platform, errorCode)`; never render raw provider JSON/messages. Each platform has explicit mappings for authorization, permission, rate-limit, provider/network failure, invalid provider response, credential/configuration failure, and unsupported/not-found cases. YouTube additionally maps `SOCIAL_COMMENTS_DISABLED`; other platforms do not assume that code unless their own adapter emits it. Unknown platform/code combinations use a generic localized fallback.
- Each expanded comment exposes its workflow history and available evaluation, suggestion, edit/save, optional response evaluation, manual-send, and platform-supported like/unlike actions. Show a hollow heart for an unliked comment and a filled red heart after a successful like; a second explicit action unlikes it. Do not render the control when the adapter reports that liking is unsupported for the comment.
- Generation is enabled only after analysis and creates variants in `pt-BR`, `en-US`, and `es-ES`; the creator selects which saved variant to review, edit, evaluate, or send. Saving appends a creator-authored response or revision; evaluation and sending use the latest saved version in that selected response lineage. When the creator sends changed editor text, save it as a new revision before dispatch; generating another language does not make the selected variant stale.
- Response-tone controls read/write the selected account's profile or the tenant-global profile through a scope switch; the account scope shows whether the account inherits the global profile or uses its own complete replacement. A successful tone or schedule save collapses its settings panel while the localized toast confirms the write; a failed save keeps the panel open. The optional response-evaluation action is visible when comment analysis and a saved response version exist; no numeric risk cue or automatic evaluation is used.
- Preferences lets the local operator configure one TypeSafe/Jev API key plus Gemini/OpenAI access and the Gemini data-use policy. There are no user-configurable JEV endpoint, auth-header, or prefix fields; the adapters use TypeSafe's documented System One endpoint and Bearer authentication. API keys are write-only password inputs: reads return configured flags, never key values; blank fields preserve existing keys, while an explicit clear action removes a saved override. The API encrypts saved provider configuration using `SOCIAL_CREDENTIAL_ENCRYPTION_KEY`; environment settings remain fallback values. The screen also loads and saves only allowlisted text-generation models through `GET/PUT /ai/response-generation/settings`.
- Show app reply state independently from external reply state. Preserve `UNKNOWN` as unknown rather than presenting it as not replied.
- Keep every screen usable at narrow viewport widths and expose loading, errors, disabled reasons, and action results accessibly. The semi-automatic dialog's approval-boundary note is plain text on the normal dialog surface, wraps without horizontal overflow, and is not a colored callout card. Keep the active “Comments” label visible in the tablet sidebar and provide a labeled mobile navigation link when that sidebar is hidden. Toolbar sync and weekly schedule actions use compact icons with accessible labels; their layout remains aligned at large font sizes. A global, keyboard-accessible font-settings button remains available on every screen and offers small, default, large, and very large text; default preserves current sizing, the choice is saved in browser-local storage, and it scales typography across the complete interface. Use theme tokens in light and dark themes.

## 2. Architectural Placement

- **Domain:** `Comment`, immutable versioned `CommentAnalysis`, append-only `CommentAnalysisCorrection`, `ResponseSuggestion` with immutable AI output and append-only `ResponseSuggestionRevision`, `ResponseEvaluation`, workflow-stage records, and per-comment `ManualReplyAttempt`.
- **Application:** on-demand comment sync; individual/batch classification and suggestion orchestration; response evaluation; human correction/edit; creator-visible stage history; and explicit per-comment sends plus confirmed send-all orchestration for individually approved replies.
- **Ports:** `CommentReader`, `CommentResponder`, comment/analysis/response repositories, `CommentEvaluator`, `ResponseEvaluator`, `ResponseSuggestionGenerator`, and a persisted provider/model selection service. `ConfiguredResponseSuggestionGenerator` dispatches to Google or OpenAI adapters.
- **Adapters:** platform comment/reply adapters, JEV adapter for its documented evaluation/intelligence responsibilities, persistence, RabbitMQ workers, and presentation.

The domain does not depend on social SDKs, JEV SDKs, or persistence libraries. See [Architecture](../architecture/architecture.md), [ADR-003](../architecture/decisions/ADR-003-jev-as-evaluator.md), and [ADR-004](../architecture/decisions/ADR-004-ai-human-control-boundary.md).

User-facing validation and failure responses use stable error codes and semantic translation keys through the [localization contract](../contracts/localization.md). UI locale is selected independently from generated content. Every explicit response-generation request produces separate `pt-BR`, `en-US`, and `es-ES` suggestion artifacts; do not translate the source comment or mutate one language variant into another. See the [localization architecture](../architecture/internationalization.md).

## 3. Logical Data and Contracts

- **Comment:** normalized top-level content associated with a tenant-owned social account and publication; retain platform, external comment/thread identifiers, author display name, text, provider-created time, `canReply`, and `canLike`. Persist app reply state and app like state separately from provider-observed state. External reply status is `REPLIED`, `NOT_REPLIED`, or `UNKNOWN`; adapters report `UNKNOWN` when they cannot reliably identify whether the connected creator replied. The database identity is `(tenantId, socialAccountId, externalCommentId)`; each successful sync updates `lastSyncedAt` and sets `expiresAt` to 30 days later. Expired rows are purged on each sync/read; periodic polling is out of Phase 1.
- Migration 019 adds `can_like` and `app_liked` and must be applied before serving comment reads or syncs because the repository queries and writes these columns. Previously synchronized rows receive `canLike = false`; an explicit manual comment sync is required to populate the provider's per-comment like capability. The application does not resync comments in the background.
- **CreatorCommentReply:** optional normalized direct reply to a top-level comment, stored only when its author is reliably identified as the connected account owner. Preserve the external reply ID, parent comment ID, nullable text, provider-created time, and last synchronization time. Do not import replies from other commenters or deeper reply threads. Reply rows are tenant/account-scoped, idempotent, and deleted with the parent comment under the same 30-day retention policy.
- **CommentAnalysis:** immutable normalized TypeSafe/Jev output including sentiment/emotion/intent/topic, spam/toxicity probabilities, estimated engagement potential, need-for-external-facts and continuation-request probabilities, per-question Choice/Score confidence and probability distributions, provider/model, internal schema version, optional token usage, bounded source context, and generated timestamp. Explicit continuation requests use intent `CONTENT_REQUEST` and contribute to the engagement estimate. `entity` and free-text rationale are nullable because System One does not perform arbitrary text extraction or generate explanations. `engagementValue` is a model estimate, not an observed platform metric.
- **CommentAnalysisCorrection:** append-only human correction of sentiment/emotion/intent/topic/entity and spam/toxicity/engagement values (scores stay in `[0,1]`). It references the original analysis; TypeSafe probabilities, per-question confidence, usage, and raw evidence cannot be edited. Record changed fields, actor source (`LOCAL_PILOT` until Phase 3), timestamp, and optional reason.
- **ResponseToneProfile:** configuration resolvable at two scopes — a tenant-global default and a complete per-account replacement — with one primary tone (`FRIENDLY`, `PROFESSIONAL`, `CASUAL`, `EMPATHETIC`), up to two modifiers (`CONCISE`, `WARM`, `ENTHUSIASTIC`), and an optional note limited to 500 characters. The effective profile resolves account → tenant → Friendly default; scopes are never merged. It is independent from the global provider/model selector.
- **ResponseSuggestion:** immutable AI-generated text and source context associated with the original comment; generation requires a prior comment analysis. One explicit request creates separate variants in `pt-BR`, `en-US`, and `es-ES`. Each variant preserves provider/model, language, confidence, rationale, timestamp, the exact `ResponseToneProfile` snapshot used, and the scope that supplied it (`ACCOUNT`, `TENANT`, or `DEFAULT`).
- **CreatorAuthoredResponse:** creator-entered response text that has no AI-suggestion parent and does not require comment analysis. Every edit is append-only and preserves the exact text/version and actor source (`LOCAL_PILOT` until Phase 3).
- **ResponseSuggestionRevision:** append-only creator edit linked to its AI suggestion and prior revision, containing the exact manual text, actor source, timestamp, and optional reason. Never overwrite the AI-generated text.
- **ResponseEvaluation:** optional manually requested structured TypeSafe/Jev output for normalized relevance, tone, helpfulness, factual/toxicity/hallucination probabilities, advisory recommendation, per-question evidence, model/token usage, internal schema version, and timestamp. Rationale is `null`; the result is advisory and never a send gate.
- **ResponseGenerationSettings:** one global pilot selector containing provider (`google` or `openai`) and an allowlisted model. Provider keys are not part of this selector; they are stored separately in the encrypted AI-provider settings record and never returned. `updatedByAdminUserId` is nullable until Phase 3 admin authentication is connected.
- **CommentWorkflowEvent:** append-only per-comment timeline event for sync/classification/correction/generation/creator-authored text/edit/optional response evaluation/send/like, with operation/batch ID, status, source, timestamp, parent artifact/event ID, and normalized structured payload. Each manually initiated phase creates auditable per-comment results. Events expire with their associated comment after 30 days and are removed by the comment-retention cascade.
- **BatchOperation:** user-initiated grouping with scope (`COMMENT`, `PUBLICATION`, `ACCOUNT`, or `PLATFORM`), requested operation, and child comment-operation IDs. `PLATFORM` is limited to the selected social network and never crosses networks. Every child completes/fails independently; batch state is derived from its children and never substitutes for detailed results. Cross-platform `all` scope is unavailable in the initial UI/API contract.
- **ManualReplyAttempt:** append-only per-comment explicit send action linked to the exact final saved response version (AI-generated/edited or creator-authored), recording actor source/time, capability check, exact text, optional response-evaluation event, external outcome/ID, and stable attempt ID. A second attempt for the same version is blocked after any recorded attempt; ambiguous outcomes require reconciliation outside the application. The semi-automatic dialog creates no batch attempt or endpoint; it serially invokes the per-comment route after one final confirmation.

The normalized `PlatformComment` carries `platform`, `externalCommentId`, `externalThreadId`, `externalPublicationId`, nullable `authorDisplayName`, nullable `text`, nullable ISO `createdAt`, `canReply`, `canLike`, and platform reply-state evidence. The normalized comment page also carries eligible direct `CreatorCommentReply` records and an opaque `nextCursor`; provider cursors/DTOs remain inside adapters. A generic non-zero reply count is not evidence that the connected creator replied. The application separately persists whether it sent a reply or liked a comment; app state is never overwritten by provider sync. `CommentReader.getComments(account, publicationId, cursor?)` returns a normalized page. `CommentResponder.reply(account, comment, editedText)` returns the external reply identifier. Replies and likes must check the normalized capability and exact platform authorization before making a write request; tokens are resolved from the credential vault inside infrastructure and never enter response DTOs/logs.

## 4. Comment Ingestion and Evaluation Flow

1. The browser requests an on-demand comment sync for one listed publication/video or the current visible publication page. The existing batch API may still execute an explicitly requested platform-scope sync, but the browser's main sync control does not invoke it; periodic polling remains out of Phase 1.
2. Resolve each applicable social account within the fixed pilot tenant and check read-comment capability/authorization.
3. Fetch provider pages through `CommentReader`, preserving the provider cursor for subsequent requests.
4. Normalize each top-level comment and any direct reply by the connected account owner. Upsert comments by `(tenantId, socialAccountId, externalCommentId)` and creator replies by their external reply identity; refresh the comment's 30-day expiry only when successfully observed.
5. Remove expired rows for that tenant during sync, then return only the normalized page and opaque next cursor. A failed provider read must not alter stored comments.
6. Comment analysis/evaluation is a separate COM-06 workflow and never changes sync success semantics.

Comment reads and sync requests delete rows whose 30-day `expiresAt` has passed before returning or writing data; no background polling/cleanup worker is required for the local pilot.

### Per-comment workflow stages and batch actions

- The screen is organized by social network, publication/video, then comments. A manual refresh on one publication syncs that publication; a manual refresh at network level syncs all accessible publications on that network only. No operation syncs all networks or runs in the background.
- The creator manually requests comment analysis or AI response generation per comment, per publication/video, or for selected items on one network. Network-level execution is serial and returns independent per-comment results; failures do not cancel or hide other outcomes. Standalone phases require separate creator requests. The per-video semi-automatic dialog is an explicit composite request for analysis-if-needed followed by generation; it does not run after any other action automatically. Its separate send-all action sends only individually approved, saved rows after a final confirmation, serially through the existing per-comment endpoint; it does not create a batch-send endpoint or combine audit events.
- Bulk mode never combines comments into a single AI artifact. Each JEV/generator call and audit record remains per comment.
- `GET /social/accounts/{accountId}/publications/{publicationId}/comments` returns persisted top-level comments, persisted direct creator replies, and app/external reply states for the selected content.
- Each collapsed comment shows its text and reply state; expanding it exposes the relevant manual actions and results. Track `SYNCED`, `CLASSIFIED`, `CORRECTED`, `SUGGESTED`, `MANUALLY_AUTHORED`, `REVISION_EDITED`, optional `EVALUATED`, and `SENT` as applicable, with per-operation status, source, timestamp, and stable failure code.
- Persist app reply state independently from external reply state. Only a direct reply authored by the connected account owner counts as an external creator reply; replies from other commenters do not. External status is `REPLIED`, `NOT_REPLIED`, or `UNKNOWN`; use `UNKNOWN` where the platform cannot reliably identify the creator or enumerate the relevant replies. Do not infer creator reply status from a non-zero count of any replies. The UI reports responded if either the app-sent state or confirmed external creator-reply state is true, while preserving their separate sources.
- Preserve the original TypeSafe `CommentAnalysis`, including per-question probabilities/confidences and token usage. Creator corrections may change sentiment/emotion/intent/topic/entity labels and spam/toxicity/engagement values in `[0,1]` only; persist an append-only correction with actor source, timestamp, corrected fields, and optional reason. Never rewrite the original signal evidence.
- AI response generation is available only after comment analysis. Creator-authored response text is independent of comment analysis. Keep AI output immutable; creator-authored response roots and all later edits are separately append-only and auditable.
- Response evaluation is a separate optional manual action and requires comment analysis. It evaluates the latest saved version in the selected response lineage; a later edit or newer generation of that language makes the prior version stale for evaluation but does not erase its history. Generating a different language variant does not stale it. Evaluation output is advisory only, including `REJECT`; it never blocks an explicit manual send.
- `POST /social/accounts/{accountId}/comments/{externalCommentId}/revisions/{revisionEventId}/send` accepts no body or caller-supplied text. It sends only the exact latest saved version in the selected response lineage, rechecks reply capability/authorization, appends an `IN_PROGRESS` attempt before calling the platform, and stores a separate result event. A later edit or newer generation of the same language makes an older AI version stale; another language does not. Any prior attempt for that version blocks another attempt, including ambiguous outcomes. The semi-automatic “send all approved” button invokes this per-comment route sequentially and requires a final confirmation; no alternate batch API is added.
- `POST /social/accounts/{accountId}/comments/{externalCommentId}/like` accepts `{ "action": "LIKE" | "UNLIKE" }`, uses the account's saved authorization, and returns the app-owned liked state. It is an explicit per-comment action, not a batch or AI workflow. In Phase 1, expose it for Facebook Pages and TikTok Business comments only; YouTube has no comment-rating write method, and Instagram requires the Facebook Login `instagram_manage_engagement` flow which the current Instagram Login integration does not provide.
- `GET /social/comments/summary` returns persisted comment counts for the resolved tenant — never a caller-supplied tenant ID. Its view lists one `{ platform, totalComments, unansweredComments, unevaluatedComments, sentRepliesToday }` entry per platform that has comments, plus a `totals` object summing all platforms. `unansweredComments` counts comments with `appReplied = false` and `externalReplyStatus = 'NOT_REPLIED'`; `unevaluatedComments` counts comments with no non-failed `COMMENT_ANALYSIS_CREATED` event; `sentRepliesToday` counts successful `MANUAL_REPLY_RESULT` events recorded on the current UTC day. Expired comments and events are excluded. It is a read-only aggregation; it does not sync, evaluate, or send anything.

## 5. Response Suggestion and Decision Flow

1. For AI generation, require an existing comment analysis, resolve the effective tone profile for the connected social account (account profile, else tenant-global profile, else Friendly default), and invoke the configured `ResponseSuggestionGenerator` only after the creator explicitly requests generation. Snapshot the profile and its source on the immutable suggestion event.
2. For creator-authored text, allow direct entry without comment analysis and persist it as a distinct manual response version.
3. Let the creator edit either response kind; each save appends an exact-text version and never overwrites prior AI or creator text.
4. If a comment analysis exists, the creator may manually request a response evaluation for the exact latest version in the selected response lineage. Validate and append the structured TypeSafe result; do not run it automatically on generation or edit.
5. Display evaluation recommendation, risk probabilities, per-question confidence, and evidence as advisory information. Rationale is `null`. `APPROVE`, `REVIEW`, or `REJECT` never dispatches or blocks a manual send.
6. Only after an explicit per-comment send or final confirmation of the semi-automatic send-all action, validate platform reply capability and account authorization for each comment, then invoke `CommentResponder` with the exact latest saved text in the selected response lineage. The send-all action includes only individually approved saved versions and invokes the existing per-comment route serially. Persist changed editor text as a revision first; append the attempt before dispatch and persist/display the external result.

Every Phase 1 external response requires explicit creator action. Spam/toxicity scores and response-evaluation results do not trigger actions or block an explicit send; the creator remains responsible for the final text. A send-all request is limited to individually approved saved responses and requires a separate confirmation. Requests are sent serially; individual failures do not cancel later rows, but a platform rate-limit response halts the remaining queue. Failed/ambiguous attempts are not retried automatically. Do not add randomized delays to disguise automated traffic; any future pacing must follow documented platform limits. No background reply, configurable communication-policy schema, or numeric risk threshold is part of this controlled pilot. The frontend shows the optional response-evaluation action when its documented preconditions are met; it does not infer a risk threshold.

### Response-generation model selection

- The local pilot exposes `GET/PUT /ai/response-generation/settings` for a global provider/model selector. The initial catalog is Google `gemini-3.5-flash-lite` and OpenAI `gpt-6-luna`; Gemini is seeded as the default.
- Updates accept only an allowlisted `provider` and `model`; API keys are not accepted by the endpoint or stored in PostgreSQL. The selector is unauthenticated only while bound to loopback; Phase 3 must protect it with the platform-admin principal and populate `updatedByAdminUserId`.
- `ConfiguredResponseSuggestionGenerator` reads the persisted selection per request and dispatches to the corresponding provider adapter. API keys are resolved lazily from encrypted Preferences settings, falling back to `GEMINI_API_KEY` or `OPENAI_API_KEY` when no saved key exists. The response-generation use case invokes it independently for `pt-BR`, `en-US`, and `es-ES`, recording success/failure per variant.
- Gemini Free-tier use also requires the saved Preferences policy or `GEMINI_DATA_USE_POLICY=free-tier-acknowledged`; alternatively select `paid-tier`. This records operator policy acknowledgement, not provider account verification.
- Preferences loads provider-key presence flags, Gemini data-use policy, and encrypted-settings storage readiness. It never returns keys; replacement keys are accepted only on write and masked in the browser. The JEV section presents one TypeSafe/Jev key and the fixed provider, not endpoint/header/prefix fields.
- `GET/PUT /ai/provider-access` exposes only configured flags and write-only provider keys/policies. `PUT` encrypts saved settings at rest and never returns secrets. Empty key inputs preserve existing saved values; explicit clear flags remove saved key overrides. Save is rejected with a stable error when the credential encryption key is missing or invalid. Legacy encrypted JEV endpoint/header fields are ignored during restore so existing saved keys remain readable.
- Preferences offers the complete allowlisted provider/model catalog and persists selection through the existing response-generation settings API. A failed load/save is shown as an actionable error and never implies a selection was saved.

### Hierarchical response tone configuration

- `GET/PUT /social/settings/response-tone` reads or updates the tenant-global tone profile — the default applied to every account without its own profile. `GET/PUT /social/accounts/{accountId}/response-tone` reads or updates the account profile; the account `GET` returns the effective profile plus its source (`ACCOUNT`, `TENANT`, or `DEFAULT`). Neither route changes the global provider/model selector, and neither accepts a caller-supplied tenant ID.
- Profile values: one primary tone (`FRIENDLY`, `PROFESSIONAL`, `CASUAL`, `EMPATHETIC`), up to two distinct modifiers (`CONCISE`, `WARM`, `ENTHUSIASTIC`), and an optional creator note of at most 500 characters. The unset default is `FRIENDLY` with no modifiers or note.
- Scope settings by `(tenantId, socialAccountId)` for accounts and `tenantId` for the global profile. Validate account ownership before account read/write. Store no provider secrets in this configuration.
- A saved account profile is a complete replacement of the global profile for that account only; primary tone, modifiers, and note are never merged across scopes. Changing the global profile affects only accounts without their own profile.
- Every generation request supplies the effective profile to the selected AI provider and snapshots the exact profile and its source in its append-only suggestion event, so later setting changes never rewrite history. A validated one-time generation override may replace the primary tone for one comment while inheriting the effective modifiers and note; it does not update account or global settings.
- Tone is a style preference only. Manual response text is untouched, generation remains explicit and requires comment analysis, and tone never authorizes send or overrides factuality/platform/manual-send rules.

## 6. Asynchronous Work and Failure Handling

Phase 1 comment reads are initiated on demand and persist normalized pages synchronously; the upsert is idempotent so a retry does not duplicate comments. RabbitMQ may be used for separate comment/response evaluation workflows, not required to render a fetched comment page.

- Read unsupported or revoked access: return an explicit result and do not call the provider.
- Social/JEV timeout: retain existing state and surface retryable/non-retryable failure according to a policy still to be defined.
- Invalid structured AI output: reject the analysis/evaluation; do not mutate the associated domain entity.
- Unsupported reply operation: persist/report unsupported; make no external reply request.
- Ambiguous reply result: persist the ambiguous outcome and do not retry automatically; a prior attempt blocks another send for the same revision. Provider reconciliation/idempotency support is platform-specific and remains TBD.
- TypeSafe/Jev's documented endpoint/auth contract is shared by classification and response evaluation; live requests remain opt-in and must use deterministic mocks in routine tests.
- Spam/toxic signals never trigger generation or sending. A creator may explicitly request a suggestion after comment analysis; the signals remain part of the analysis context and do not automatically block a deliberate manual send.

## 7. Security, Privacy, and Observability

- JEV receives only application-prepared context; it cannot query the database, social APIs, RabbitMQ, or object storage.
- Minimize author context sent to JEV and retain only data required by product policy/platform terms.
- Never log access tokens or unredacted secrets. Restrict provider payload logging and preserve audit data for analysis/evaluation decisions.
- Trace sync/evaluation/reply operations by internal comment, publication, and analysis identifiers, with provider and outcome categories.

## 8. Verification

Apply Clean Code and TDD (Red-Green-Refactor): write or update a failing test before production changes, implement the smallest suitable change, then refactor with tests green. Every use case requires unit tests; critical user journeys require E2E coverage.

- **Unit:** normalization/identity, analysis schema and versioning, invalid-output non-mutation, creator-policy/risk decision, capability gating, sequential current-page sync progress/partial failures, and platform/error-code message mapping with a generic fallback.
- **Integration:** per-platform comment and reply adapters; page-size mapping for publication readers; JEV request/response schema boundary; repository persistence; RabbitMQ consumers.
- **E2E:** page-size query defaults/allowlist, cursor pagination, sync limited to the current publication page, visible progress, and stable provider error codes; the semi-automatic dialog syncs only its selected video, excludes confirmed replied and `UNKNOWN` comments, evaluates/generates per comment with independent failures, snapshots one-time tone overrides, preserves AI text when edits are saved, and confirms that approval itself never sends. A separate confirmed send-all action sends only approved/saved/capable rows sequentially through the per-comment endpoint, displays per-comment outcomes, continues after individual failures, stops on rate limit, and does not retry ambiguous attempts. Also cover positive/question/complaint/spam/toxic/ambiguous/low-confidence comments; unsupported reply creates no provider call; high-risk response cannot auto-publish. Use deterministic social/JEV test doubles, not production services or live model output.
- **Frontend unit:** the global font preference applies four supported sizes to the document root, persists safely in browser-local storage, has translated labels in all supported locales, and remains accessible and responsive on every screen. At large and very large sizes, toolbar actions remain aligned on one row on desktop, reflow without overlap on narrow screens, and the page-size label can wrap.
- **Like interaction:** the heart appears only when `canLike` is true, sends exactly one explicit `LIKE` or `UNLIKE` action, turns red only after a successful like, retains state after reload, and shows a localized failure without changing local state when the provider rejects the action. Cover Facebook Pages and TikTok with deterministic provider doubles; verify no like request is made for YouTube or the current Instagram Login integration.
- AI outputs are validated deterministically and are not treated as a test oracle; follow [Test Strategy](../validation/test-strategy.md) and [AI Evaluation Matrix](../validation/ai-evaluation-matrix.md).
